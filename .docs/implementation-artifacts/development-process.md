# Development process and quality assurance

This document records verifiable facts about how Studieplan was developed with AI assistance and BMAD. It is not the student's personal reflection report and does not claim personal learning, user value, or experience that has not been documented.

## Scope and control

The work was divided into bounded deliveries. The initial local study planner was extended with calendar views, capacity planning, controlled imports, work history, dependencies, and student-approved replanning. The later full-stack delivery was explicitly limited to a local Node API, authoritative SQLite storage, controlled migration of browser data, Docker packaging, and documentation. Further institution coverage was paused rather than treated as complete.

The implementation had to preserve stable IDs, relationships, import provenance, history, and existing browser data. It also had to keep planned time, recorded work, remaining work, completed work, and manually confirmed submission as separate concepts. Docker and browser checks used synthetic data, isolated ports, project names, and volumes so port 80 and actual user storage were not changed. The approved technical boundaries are recorded in the [full-stack specification](spec-fullstack-database-docker-delivery.md) and the [architecture](../planning-artifacts/architecture/architecture-studieplanlegger-2026-09-06/ARCHITECTURE-SPINE.md).

## Use of AI and BMAD

AI assisted with requirement structuring, architecture, implementation, tests, fault investigation, Docker configuration, and documentation drafts. BMAD supplied explicit specifications, frozen scope boundaries, implementation handoffs, independent review layers, and verification gates. Suggestions were not treated as verified merely because they were generated: accepted changes were compared with the code and requirements, exercised by targeted tests, or confirmed in an observed runtime check.

For example, the full-stack review used blind, edge-case, and verification-gap layers. Each reported claim was checked against the specification and implementation, then recorded with evidence as accepted, rejected, or externally blocked. Bounded accepted findings were corrected and the affected checks were repeated before completion; unsupported or disproportionately broad suggestions were not silently implemented. The decisions remain visible in the [full-stack review triage log](spec-fullstack-database-docker-delivery.md#review-triage-log).

One example was the initial failure to start BMAD through `uv` in the agent context. The failure was separated into executable, command/path, and permission possibilities. The existing installation and required generator later ran through the environment's narrow approved mechanism with exit code 0, without reinstalling `uv` or changing file associations or security settings. The dated runtime record is in [VERIFICATION.md](../../studieplanlegger/VERIFICATION.md#docker-transport-follow-up--2026-09-20).

Studieplan itself does not call a generative-AI service at runtime. Its suggestions are produced from registered data and deterministic rules. The locally shipped illustration is a static development asset, and the bundled fonts retain the [SIL Open Font License](../../studieplanlegger/public/fonts/OFL.txt).

## Concrete findings and corrections

- Early database review found missing relational `REFERENCES`, incorrect migration eligibility for settings-only state, and insufficient purge coverage. The correction added relational foreign keys, included settings in the authoritative empty-state decision, and tested privacy purge across valid legacy archives as well as live/recovery work history.
- The Docker base-image transfer initially failed with `local error: tls: bad record MAC`. This was recorded as an observed transport failure rather than assigned an unsupported cause. When the image became available, the real Compose build, health check, browser flow, backup/restore, and same-volume recreation were completed and documented.
- Submission review found that privacy purge missed work history inside valid legacy archives, database E2E lacked a dedicated repeatable command, skipped Playwright suites could appear successful, `.woff2` lacked an explicit MIME type, and a calendar calculation used `clientTop` instead of `clientLeft`. These findings were corrected and retested before the final clean Docker checks.
- A representative older SQLite database without `state_meta.shape_json` reproduced `table state_meta has no column named shape_json` even though the existing suite was green. Migration was changed to create compatibility columns before using them and to keep schema upgrade and validation in one transaction. The regression cases in [database-delivery.test.js](../../studieplanlegger/tests/unit/database-delivery.test.js) cover content preservation, repeat opening, a fresh database, an intermediate schema, and rollback on an invalid legacy relation; the implementation is in [database.js](../../studieplanlegger/server/database.js).
- Repository-hygiene review removed unnecessary generated BMAD screenshots and validation artifacts from the submitted tree while retaining source, tests, licences, and factual process evidence. Exact ignore rules were extended for databases, private environment files, backups, browser profiles, and generated output; archived originals remained local and in Git history. The dated control is recorded in [VERIFICATION.md](../../studieplanlegger/VERIFICATION.md#repository-opprydding--2026-09-20).
- Documentation review corrected an outdated claim of 47 adapters and unresolved AHO coverage. The current evidence records 48 adapters among 49 mapped institutions, but this is not complete programme, cohort, study-semester, calendar-semester, campus, group, or personal-timetable coverage. Ekko still lacks a suitable independent historical catalogue, several calendar sources require access or have observed source failures, and the Sikt route requires approved Maskinporten access. The exact current scope is in [IMPORT-COVERAGE.md](../../studieplanlegger/IMPORT-COVERAGE.md).
- Review suggestions for broader timezone support, asynchronous storage, and additional size limits were not implemented in that review because they require wider product or migration decisions. Recording a deferral is not evidence that the limitation has been solved.

These are documented project events. They do not establish who personally discovered each issue or what the student learned from it.

## Verification and evidence limits

On 20 September 2026, the [final legacy-migration correction](../../studieplanlegger/VERIFICATION.md#legacy-shape_json-migration-correction--2026-09-20) passed 1200/1200 unit tests in 95 files, a 68-module production build, and 2/2 production database E2E cases. The separate [Docker clean-copy acceptance](../../studieplanlegger/VERIFICATION.md#docker-clean-copy-runtime-acceptance--2026-09-20) confirmed a healthy non-root container, loopback-only publication, SQLite writes, stable course/task/session IDs and relationships after forced container recreation with the same named volume, and a separate Chromium context without the application's local-storage record. Backup restore returned the earlier state while preserving identities and retained the replaced state as recovery evidence. The linked sections distinguish these final results from earlier 1195/1196-test runs and preserve failures that were later superseded.

Technical tests show only the exercised behavior. They do not demonstrate the student's understanding, learning outcome, study habits, perceived usefulness, long-term operation, protection from disk failure, or outcomes for other students. Recovery is not a substitute for a separate backup. Vite development mode uses `localStorage` and is not evidence of SQLite production persistence; a proposed or elapsed study session is not evidence that work occurred; completed work is not evidence of submission.

Historical acceptance of basic functions on 6–7 September and a later short example flow concerned narrower earlier versions. A Codex trial used synthetic tasks. No completed month of personal use was recorded, so blank trial fields and unanswered personal-reflection questions have not been converted into claims about the current application.
